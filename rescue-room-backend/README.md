# Rescue Room Backend — Stage 1

An isolated local session-tracking API. This project does not read, serve, modify, or connect to `../rescue-room`. No admin UI, authentication, payments, prizes, ads, or runtime external services are included.

## Build and run

Use a JDK 21 or newer supported by Spring Boot 4.1.1, with `JAVA_HOME` pointing to that JDK. The included official Maven wrapper supplies Maven 3.9.16; initial builds require internet access to fetch build dependencies.

From **this directory**:

```powershell
.\mvnw.cmd clean verify
.\mvnw.cmd spring-boot:run
```

On macOS/Linux: `./mvnw clean verify` and `./mvnw spring-boot:run`.

Or run the packaged application after building:

```powershell
java -jar target/rescue-room-backend-0.0.1-SNAPSHOT.jar
```

The API binds to **127.0.0.1:8081**. The game server on port 4173 is independent. No cross-origin game access is configured.

## Database and model

H2 file URL: `jdbc:h2:file:./data/rescue-room;DB_CLOSE_ON_EXIT=FALSE;WRITE_DELAY=0`. Run from this backend directory so database files stay under `rescue-room-backend/data/`. The file persists across application restarts. Committed writes are flushed without H2's default delay, including the last email update before a process restart ([H2 write-delay documentation](https://h2database.com/html/commands.html#set_write_delay)). Local credentials are `sa` with an empty password; the H2 browser console is not included or enabled.

`schema.sql` creates `game_sessions` if absent. Hibernate validates that the model matches the schema; it does not silently alter existing tables. Database files and build caches are ignored by Git. Tests use a separate in-memory H2 database.

| Column | Type | Rules |
| --- | --- | --- |
| `id` | BIGINT identity | Internal primary key |
| `session_id` | UUID | Required, unique public identifier |
| `status` | VARCHAR(16) | PLAYING, WIN, LOSE |
| `email` | VARCHAR(254) | Nullable until submitted |
| `started_at` | Timestamp with time zone | Required, immutable |
| `finished_at` | Timestamp with time zone | Null until WIN/LOSE |
| `remaining_seconds` | INTEGER | Null while PLAYING; 0–90 for WIN; 0 for LOSE |
| `last_seen_at` | Timestamp with time zone | Set at start, heartbeat, and finish |

All timestamps use a server-side UTC `Clock`, normalized to microseconds so API responses round-trip through H2 unchanged. Persistence goes through `GameSessionRepository` and transactional `GameSessionService`. Update operations take a database row lock, so concurrent finishes cannot both succeed or overwrite the first result. Database constraints also enforce unique public IDs, status values, remaining-time bounds, and consistent finished/unfinished fields.

## API contract

Every successful response contains all eight model fields. IDs are generated by the server; clients cannot set status or timestamps directly.

| Method | Path | JSON body | Result |
| --- | --- | --- | --- |
| POST | `/api/sessions/start` | None | 201, new PLAYING session and `Location` header |
| GET | `/api/sessions/{sessionId}` | None | 200, current session |
| POST | `/api/sessions/{sessionId}/heartbeat` | None | 200, updates lastSeenAt while PLAYING |
| POST | `/api/sessions/{sessionId}/win` | `{"remainingSeconds":23}` | 200, WIN with finish time and submitted remaining seconds |
| POST | `/api/sessions/{sessionId}/lose` | None | 200, LOSE with finish time and zero remaining seconds |
| POST | `/api/sessions/{sessionId}/email` | `{"email":"player@example.com"}` | 200, saves/replaces email in any status |

### Validation and transitions

- A canonical UUID is required (case-insensitive hex). Malformed or missing IDs return **400**. A valid UUID with no stored session returns **404**.
- Only `PLAYING → WIN` and `PLAYING → LOSE` are permitted. All subsequent finish attempts, including the same outcome, return **409** without changing the result. Heartbeats after completion also return **409**. GET and valid email updates remain allowed.
- WIN requires an integer `remainingSeconds` from **0 through 90**, inclusive. Missing/null, fractional, non-numeric, out-of-range, malformed JSON, and unknown JSON fields are rejected with **400**.
- Email is required in the email request, trimmed, nonblank, at most 254 characters, and syntactically validated. Null/blank input cannot clear an email. A later valid submission replaces it; email updates do not change the game status or timestamps. No email is sent and ownership is not verified.
- Errors use `application/problem+json`, with `status`, `title`, and `detail`; field-validation errors also include an `errors` map.

Example local lifecycle:

```powershell
$session = Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8081/api/sessions/start
$sessionId = $session.sessionId
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8081/api/sessions/$sessionId/heartbeat"
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8081/api/sessions/$sessionId/win" -ContentType application/json -Body '{"remainingSeconds":23}'
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8081/api/sessions/$sessionId/email" -ContentType application/json -Body '{"email":"player@example.com"}'
Invoke-RestMethod -Uri "http://127.0.0.1:8081/api/sessions/$sessionId"
```

## Tests and scope

`SessionLifecycleTests` starts the real HTTP server on a random port and uses the actual repository, transactions, validation, and in-memory H2. It checks starts/uniqueness, persisted reads, heartbeats, both outcomes, invalid transitions, concurrent outcomes, all ID failure paths, email validation/updates, malformed bodies, and remaining-time bounds. A controllable UTC clock avoids sleeps in timestamp assertions.

This stage records client-reported outcomes. It does not verify puzzle answers, enforce the 90-second deadline server-side, auto-expire abandoned sessions, send email, or authenticate callers. These are deliberately outside this foundation. Schema migrations are not yet introduced: changes to an existing schema require a future explicit migration. Do not connect the game or begin Stage 2/admin work without approval.
